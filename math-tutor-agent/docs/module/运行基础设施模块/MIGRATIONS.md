## 1. 当前策略

项目仍处于上线前开发阶段。原来的多份演进迁移已经合并为一份“当前结构基线”：

- revision：`20261031_0035`
- 文件：`migrations/versions/20261031_0035_current_schema_baseline.py`
- `down_revision = None`
- 适用数据库：MySQL 8.0

基线表示“从空数据库直接建立当前系统所需的完整结构”。它不再保留开发早期每一次加表、改列和回填的过程。

保留原 revision `20261031_0035` 的原因是：现有开发数据库已经记录了这个版本。替换文件名和迁移内容后，现有数据库仍会被 Alembic 识别为最新版本，不需要降级、重建或重新执行基线。

## 2. 当前基线包含什么

当前基线一次创建：

- 身份认证、学生、家长授权和账号会话；
- 教学会话、消息、Agent 执行轨迹和结构化学习记录；
- 知识目录、知识点、知识内容和先修关系；
- 题库、题解、验证证据、状态流转和生成批次；
- RAG 文档、切片、检索投影和索引维护任务；
- 内容问题报告、重新验证和人工复核对象；
- 数学思想与方法目录；
- 当前全部外键、唯一约束、检查约束和索引；
- 大学高数 MVP 范围约束。

“数学思想与方法”的首批分类和方法属于系统初始参考数据，随基线写入。大学高数知识目录及管理员维护的知识内容通过独立的 `math-tutor-catalog` 命令导入，避免把持续变化的业务内容固化在数据库结构迁移里。

## 3. 首次建立数据库

先在 MySQL 中建立空数据库和权限受限的应用账号，再在 `.env` 中配置：

```dotenv
DATABASE_URL=mysql+pymysql://math_tutor:password@localhost:3306/math_tutor?charset=utf8mb4
```

从 `math-tutor-agent` 目录执行：

```bash
alembic upgrade head
alembic current
```

预期当前版本为：

```text
20261031_0035 (head)
```

结构建立完成后，再初始化开发账号和知识目录：

```bash
python -m app.demo_accounts_cli
math-tutor-catalog
```

## 4. 现有开发数据库

现有开发数据库已经升级到 `20261031_0035`，本次整理不会对它执行任何 SQL，也不会删除其中的数据。

只需查看版本：

```bash
alembic current
alembic heads
```

两者都应指向 `20261031_0035`。不要对现有数据库执行 `downgrade base` 后再升级，因为基线的降级会删除项目业务表。

如果某个本地数据库结构完整，但 `alembic_version` 丢失，只能在人工核对结构与基线一致后执行：

```bash
alembic stamp 20261031_0035
```

`stamp` 只记录版本号，不会创建表、修改字段或恢复数据。

## 5. 本地固定启动流程

项目启动脚本会按固定顺序执行：

1. 启动 MySQL、Redis、Qdrant 和 Embedding 服务；
2. 执行 `alembic upgrade head`；
3. 初始化开发账号；
4. 幂等同步大学高数知识目录；
5. 确认 Qdrant collection；
6. 启动 API、学生端和管理端。

统一命令：

```bash
./scripts/dev-stack start
```

因为现有数据库已经记录 `20261031_0035`，启动时的 `upgrade head` 只会检查版本，不会重跑基线。

## 6. 上线前如何修改结构

在首次共享部署或正式上线以前，可以继续把最终模型整理回当前基线，但每次都必须满足：

1. 只在确认没有其他共享数据库依赖旧基线时修改；
2. 基线必须能从空 MySQL 数据库创建完整当前结构；
3. 现有开发数据库需要单独人工同步结构，不能依赖已经执行过的同 revision 基线再次运行；
4. 结构变化和业务数据变化分开处理；
5. 修改后同步更新本文档。

这一阶段修改基线适合减少无意义的开发演进文件，但它不会自动修改已经存在的开发数据库。

## 7. 上线后如何维护迁移

一旦项目进入共享测试、预发布或生产环境，`20261031_0035` 基线必须冻结，不再修改。之后每次数据库结构变化都新增 revision：

```bash
alembic revision --autogenerate -m "describe schema change"
```

生成后必须人工检查：

- 升级与回滚顺序；
- MySQL 无符号整数、JSON 和 `DATETIME(6)`；
- 外键的 `ON DELETE` 行为；
- 索引、唯一约束和检查约束名称；
- 新增非空字段的历史数据回填；
- 是否误删表、列或约束；
- 大表改列和建索引可能产生的锁表时间。

生产发布顺序为：备份数据库、执行 `alembic upgrade head`、确认版本和就绪检查、再发布依赖新结构的应用代码。

## 8. 查看状态与回滚

常用只读命令：

```bash
alembic current
alembic heads
alembic history --verbose
alembic show head
```

当前只有一个基线版本。对空白临时数据库可以执行：

```bash
alembic downgrade base
```

该操作会删除基线创建的全部业务表。包含真实数据的开发、预发布或生产数据库不得用这种方式回滚，应使用备份恢复或新增修复迁移。

Alembic 只管理 MySQL。Qdrant collection、Redis 缓存和外部文件不会随 MySQL downgrade 自动删除。

## 9. 迁移与备份的区别

迁移文件记录“数据库结构如何建立或变化”，例如建表、加字段、建索引和必要的数据转换。它不是数据库备份，不保存用户账号、学习记录、管理员后来编辑的知识内容或完整题库数据。

要恢复真实业务数据，仍需要 MySQL 备份。要让一套新环境具备初始目录内容，则使用项目提供的幂等初始化命令。
