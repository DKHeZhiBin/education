# 数学教育多 Agent 系统设计

## 系统设计

这是一个围绕“让学生真正学会解题”构建的多 Agent 系统。由**教学编排 Agent**统筹任务，根据当前情况调用专职 Agent；专职 Agent 通过结构化结果交接，不互相自由聊天。对学生始终呈现一个连续、统一的辅导老师。

```text
学生输入
   ↓
教学编排 Agent
   ├─ 题目理解 Agent（必要时调用 OCR）
   ├─ 解题分析 Agent
   ├─ 解答校验 Agent
   ├─ 学情诊断 Agent
   ├─ 提示教学 Agent ─────┐
   └─ 学习记录 Agent       │ 多轮互动
                           ↓
                     学生作答/追问
```

首版重点是文字数学题与多轮引导。图片 OCR、语音、错题本和家长报告作为独立能力后续接入。腾讯云不是架构前提，具体服务由适配器选择。

## 详细流程

### Step 1 - 教学编排 Agent

- **职责**：接收学生输入，读取会话状态，判断当前需要哪个专职 Agent；维护流程顺序、超时和失败降级。
- **工具**：会话状态库、Agent 调用接口、策略配置。
- **任务**：新题目触发题目理解与解题分析；已有题目下的学生回答则优先触发学情诊断，再决定追问、提示、讲解或完成总结。
- **输出**：一个明确的下一步任务，以及供下游 Agent 使用的会话上下文。
- **边界**：不亲自解决所有任务，也不把任意工具控制权交给模型。

### Step 2 - 题目理解 Agent

- **职责**：把文字或多模态输入整理成清晰、可引用的题目表示。
- **工具**：文字解析；后续可接 OCR、公式识别、ASR。
- **任务**：提取已知条件、目标、限制、图形/表格信息；发现缺失或模糊条件时提出澄清问题。
- **输出**：`ProblemSpec 2.0`，包含规范题干、带来源的条件、结构化目标、题型候选及证据、阻断/警告歧义、澄清问题和置信度。
- **说明**：若只是文字输入且内容清楚，可跳过 OCR；不确定图中符号时先让学生确认，不能擅自猜题。
- **编排**：存在阻断歧义时暂停解题和校验；学生补充信息后重新执行题目理解，确认完整才继续。

### Step 3 - 解题分析 Agent

- **职责**：为当前题目生成正确、可解释的解题路线。
- **工具**：数学推理模型；按需使用 SymPy 等符号计算工具、数值计算器或几何工具。
- **任务**：识别知识点和解法候选，推导关键步骤，列出常见误区，并标出适合提问学生的思考节点。
- **输出**：`SolutionPlan 2.1`，包括结构化多解法、推荐路线、方法比较、答案一致性、关键突破口、学生引导问题、易错点、待校验表达式和修订来源。
- **方法约束**：不强制凑多个方法；只有策略或工具明显不同且步骤完整时才保留为独立解法。
- **边界**：解题路线只交给校验与教学 Agent；默认不直接发给学生。

### Step 4 - 解答校验 Agent

- **职责**：独立检查解题分析结果，尽量避免模型自我确认造成的错误。
- **工具**：安全 AST + SymPy、独立模型复核、代回原条件和数值反例检查。
- **任务**：先用 SymPy 独立求解、比较推荐方法步骤、代回答案并检查解集完整性；未覆盖部分再交给模型。证明题单独检查目标对应、条件使用、逻辑连续性、定理适用条件、分类完整性和结论闭合。
- **输出**：`VerificationReport 2.1`，包含通过/不通过、CAS/模型覆盖范围、逐项检查证据、发现的问题、置信度和需要修正的步骤；证明题另含阻断项、未验证主张和置信度上限。
- **边界**：确定性校验失败不能被模型覆盖；工具无法解析属于未覆盖，不等同于数学错误或通过。
- **分支**：可修订失败默认最多退回解题分析 Agent 两次，每版都重新校验；模型不可用或没有具体修订依据时立即停止，达到上限后不得降低通过门槛。

### Step 5 - 学情诊断 Agent

- **职责**：从学生当前回答中判断其理解状态和具体卡点。
- **工具**：学生当前回答，以及校验通过的解题计划；未通过解法不得作为判错标准。
- **任务**：从当前消息提取可定位原文证据，区分求助、局部作答、最终答案、证明论证和提问，并记录本轮正确点、待确认误区和不确定项。
- **输出**：`LearnerState 2.0`，包括本轮证据范围、作答类型、有效尝试、证据关联的掌握点/误区假设、置信度和建议提示等级。
- **边界**：没有证据就不生成判断；过滤能力、人格和学习习惯标签。答案一致只说明本轮结果一致，不直接等同于掌握。

### Step 6 - 提示教学 Agent

- **职责**：把已校验的解题路线和学情诊断转成符合当前阶段的一轮教学回应。
- **工具**：分级提示策略、苏格拉底式提问模板、年级语气配置。
- **任务**：根据学生卡点提供最小有效提示，并留出学生思考空间；收到新作答后让编排 Agent 开始下一轮诊断。
- **输出**：`TutorReply`，包括本轮动作、学生可见文本、提示等级、预期学生回应和是否可以展示解法。
- **提示等级**：
  1. 方向提示：只指出关注对象和思考方向；
  2. 关键关系：给一个定义、定理、性质或通用公式；
  3. 局部步骤：只展示一个操作和一个中间结果；
  4. 完整讲解：只使用已校验方案，并解释每步依据。
- **边界**：普通求助每轮最多提升一级。第四级要求解法已校验、学生明确请求，并且已有一次有效尝试或已经展示过第三级。一级至三级按服务端裁剪上下文，不能包含最终答案。

### Step 7 - 学习记录 Agent

- **职责**：在一轮辅导结束后，将有价值的学习结果整理为结构化记录。
- **工具**：错题/学习记录服务、知识点标签库。
- **任务**：记录题目、实际错因、使用过的提示、最终掌握情况及建议复习点；仅记录教学需要的数据。
- **输出**：`LearningRecord`，供错题本、学习报告和后续复习使用。
- **触发时机**：会话完成、学生主动收藏，或产品策略要求保存；不需要每轮都调用。

## Agent 之间如何协作

Agent 之间不传整段自由对话作为唯一接口，而传有版本的结构化对象：

```text
ProblemSpec → SolutionPlan → VerificationReport
                                      ↓
学生作答 → LearnerState → TutorReply → 下一轮学生作答
                                      ↓
                               LearningRecord
```

每个 Agent 的输出都由服务端 schema 校验。编排 Agent 负责状态转移、重试次数、超时、成本上限和是否继续调用；工具调用由服务端白名单控制。每个对象保留来源与会话轮次，方便定位错误发生在读题、推导、校验还是教学表达。

## 会话接口草案

### 创建辅导会话

`POST /v1/tutoring/sessions`

```json
{
  "subject": "math",
  "grade": "初中",
  "input": { "type": "text", "content": "题目内容" }
}
```

返回 `session_id`、题目确认/澄清文本和当前阶段。若有歧义，先确认题意，不启动后续解题链。

### 发送学生消息

`POST /v1/tutoring/sessions/{session_id}/turns`

```json
{
  "message": "我试过先设 x，但不知道接下来怎么做",
  "intent": "answer"
}
```

返回本轮 `TutorReply`、会话状态和是否需要学生继续作答。服务端内部记录被调用的 Agent 和耗时，但不必把内部推理链暴露给客户端。

### 获取会话

`GET /v1/tutoring/sessions/{session_id}`

用于页面刷新与断线恢复。错题本和报告采用独立资源接口，避免与对话轮次耦合。

## 技术选型

- **Agent 服务**：Python 3.11+、FastAPI、Pydantic，分别承载 API、数据校验和多 Agent 编排。
- **编排模式**：先用显式状态机与普通 Python 服务组合 Agent，不引入复杂的自治式多 Agent 框架；需要可视化工作流或长任务恢复时再评估 LangGraph 等框架。
- **模型接入**：统一 Provider 接口，各专职 Agent 可共用模型，也可按成本/能力选不同模型。
- **数据层**：MySQL 8.0 + SQLAlchemy Repository；Redis 负责锁、幂等和热点缓存，会话与 Agent 产物按用户隔离。
- **前端**：继续使用现有 React + TypeScript，通过 HTTP 对接；确定流式体验需求后再增加 SSE。
- **数学工具**：以独立 `MathTool` 适配器接 CAS/数值计算；工具结果提供校验证据，不替代证明推理。
- **多模态**：OCR、ASR、TTS 都是可选适配器，文字输入路径不依赖任何特定云服务。

## 首版建议实现范围

先落地五个角色：教学编排、题目理解、解题分析、解答校验、提示教学。学情诊断可以先作为独立 Agent 实现，也可在原型阶段先合并进提示教学 Agent；学习记录等真实需要数据沉淀时再上线。这样保留多 Agent 边界，同时控制首次实现的复杂度。

首版先支持初中/高中范围内的文字题、确认题意、学生作答、逐级提示、完整讲解与结束总结。暂缓 OCR/语音、自动发布错题报告、Agent 互相自由调用和长时间后台任务。

## 失败处理与评估

- 题目理解置信度低：向学生澄清，不猜。
- 解答校验不通过：退回分析 Agent 修订；有限次数后转为澄清或说明无法可靠确认。
- 模型超时/结构不合格：有限重试；仍失败时保留会话并给出可继续的提示。
- 工具不可用：能安全回答的题目继续；依赖计算校验的题目说明校验受限。
- 用离线题集评估读题准确、推导正确、校验发现错误、提示递进、过早泄露答案率、学生卡点识别和响应时延。
