# 功能模块与 Agent 文档编写规范

## 1. 文档目标

本规范用于指导新项目以及当前项目后续新增功能模块、Agent 和跨模块能力时应编写哪些文档。目标是让产品、研发和后续维护者能够快速理解：

- 为什么需要这项能力；
- 它负责什么、不负责什么；
- 数据和请求怎样流转；
- 正常、异常和边界情况怎样处理；
- 当前真实实现到了哪里；
- 如何运行、验证和判断是否达到上线条件。

所有文档必须区分以下三种状态：

1. **已实现**：代码、数据结构或运行流程已经存在，并能指出对应位置；
2. **已设计、待实现**：方案已经明确，但代码尚未完成；
3. **未来设想**：方向性想法，尚未形成可执行设计。

不能把设计目标写成当前已经具备的能力。

## 2. 文档分层

项目文档分为三层：

```text
docs/
├── 项目级文档
├── module/
│   └── 各功能模块文档
└── agent/
    └── 各 Agent 专项文档
```

- **项目级文档**解释整个产品为什么存在、系统怎样组成以及各模块如何协作；
- **功能模块文档**解释一组完整业务能力的数据、接口、状态和运行方式；
- **Agent 文档**解释一个 Agent 的职责、上下文、工具权限、停止条件和评估方法。

小功能不需要为每一项建立空文档。先使用最小文档组合，内容变复杂后再拆分。

## 3. 项目级文档

一个完整项目建议包含：

```text
docs/
├── README.md
├── REQUIREMENTS_ANALYSIS.md
├── SYSTEM_ARCHITECTURE.md
├── BUSINESS_FLOWS.md
├── DATA_MODEL.md
├── AGENT_COLLABORATION.md
├── TECHNICAL_DESIGN.md
├── LOCAL_DEVELOPMENT.md
├── DEPLOYMENT.md
├── LOGGING_AND_MONITORING.md
├── SECURITY_AND_PRIVACY.md
├── TEST_STRATEGY.md
└── TODO.md
```

| 文档 | 主要职责 |
| --- | --- |
| `README.md` | 提供所有文档的可点击目录、推荐阅读顺序和放置规则 |
| `REQUIREMENTS_ANALYSIS.md` | 说明用户、场景、核心问题、业务目标和产品边界 |
| `SYSTEM_ARCHITECTURE.md` | 说明模块、服务、数据库、外部依赖和总体调用关系 |
| `BUSINESS_FLOWS.md` | 按业务分别描述端到端流程，不把不同业务挤在一张图中 |
| `DATA_MODEL.md` | 说明核心数据对象、归属、关系、版本和生命周期 |
| `AGENT_COLLABORATION.md` | 说明多个 Agent 的分工、交接、隔离和编排方式 |
| `TECHNICAL_DESIGN.md` | 说明技术栈、代码分层、关键实现方案和扩展方式 |
| `LOCAL_DEVELOPMENT.md` | 说明必要配置、固定启动顺序、测试账号和排障入口 |
| `DEPLOYMENT.md` | 说明构建、迁移、发布、回滚和环境差异 |
| `LOGGING_AND_MONITORING.md` | 说明日志位置、结构化字段、指标、告警和追踪方式 |
| `SECURITY_AND_PRIVACY.md` | 说明认证、授权、数据隔离、导出、删除和敏感信息处理 |
| `TEST_STRATEGY.md` | 说明自动化测试、人工验收、评估集和上线门槛 |
| `TODO.md` | 记录实现顺序、完成状态、阻塞条件和后续计划 |

## 4. 功能模块文档

### 4.1 推荐目录

```text
docs/module/某功能模块/
├── README.md
├── REQUIREMENTS.md
├── BUSINESS_FLOW.md
├── DATA_MODEL.md
├── API.md
├── STATE_MACHINE.md
├── OPERATIONS.md
├── QUALITY_METRICS.md
└── ACCEPTANCE.md
```

### 4.2 必须编写的文档

| 文档 | 必须说明的内容 |
| --- | --- |
| `README.md` | 模块目标、负责范围、不负责范围、依赖模块和文档导航 |
| `REQUIREMENTS.md` | 用户场景、业务规则、权限、异常情况和验收标准 |
| `BUSINESS_FLOW.md` | 入口、处理步骤、条件分支、失败去向和最终产物，复杂流程使用 Mermaid |
| `DATA_MODEL.md` | 数据对象、字段含义、表关系、数据归属、版本和删除规则 |
| `API.md` | 路径、权限、请求响应、错误码、幂等、重试和调用示例 |
| `ACCEPTANCE.md` | 可以实际操作的正常流程、异常流程和边界验收清单 |

### 4.3 按复杂度增加的文档

| 文档 | 适用情况 |
| --- | --- |
| `STATE_MACHINE.md` | 存在草稿、检查、发布、隔离、退役等状态迁移 |
| `SECURITY_AND_BOUNDARIES.md` | 涉及用户数据、角色权限、跨用户隔离或外部系统 |
| `OPERATIONS.md` | 需要部署、迁移、缓存、定时任务、监控或故障恢复 |
| `QUALITY_METRICS.md` | 需要质量指标、评估方法和上线阻断条件 |
| `DECISIONS.md` | 需要记录重要方案选择、备选方案和选择原因 |
| `CHANGELOG.md` | 模块进入稳定使用后，需要追踪行为与接口变化 |

### 4.4 模块文档必须回答的问题

1. 模块解决什么问题？
2. 哪些用户或其他模块会使用它？
3. 模块的入口和最终产物是什么？
4. 哪些能力属于本模块，哪些属于其他模块？
5. 核心数据保存在哪里，归谁所有？
6. 是否存在状态迁移、版本或并发冲突？
7. 失败后重试、回滚、降级还是停止？
8. 权限和数据隔离如何保证？
9. 怎样通过日志和指标排查问题？
10. 怎样验收，什么条件下允许上线？

## 5. Agent 专项文档

### 5.1 推荐目录

```text
docs/agent/某Agent/
├── README.md
├── AGENT_SPEC.md
├── INPUT_OUTPUT.md
├── PROMPT_POLICY.md
├── TOOL_POLICY.md
├── WORKFLOW.md
├── ERROR_RECOVERY.md
├── CONTEXT_AND_MEMORY.md
├── OBSERVABILITY.md
└── EVALUATION.md
```

### 5.2 必须编写的文档

| 文档 | 必须说明的内容 |
| --- | --- |
| `README.md` | Agent 的目的、系统位置、调用方、协作方和文档导航 |
| `AGENT_SPEC.md` | 职责、禁止事项、输入前提、输出责任、成功和失败定义 |
| `INPUT_OUTPUT.md` | 输入 DTO、输出 DTO、字段含义、约束和结构化示例 |
| `WORKFLOW.md` | 内部步骤、工具顺序、决策分支、状态影响和停止条件 |
| `EVALUATION.md` | 固定评估集、质量指标、通过标准和典型失败样例 |

### 5.3 强烈建议编写的文档

| 文档 | 适用情况 |
| --- | --- |
| `PROMPT_POLICY.md` | 使用 LLM，需要管理系统提示词、提示版本和输出约束 |
| `TOOL_POLICY.md` | 会调用搜索、数据库、RAG、SymPy、OCR 或其他工具 |
| `ERROR_RECOVERY.md` | 存在重试、修订、降级、隔离或人工接管 |
| `CONTEXT_AND_MEMORY.md` | 使用会话历史、长期记忆、RAG 或学生状态 |
| `OBSERVABILITY.md` | 需要追踪模型、提示、工具证据、耗时、Token 和失败位置 |
| `COLLABORATION.md` | 与多个 Agent 存在复杂交接、并行执行或互相隔离 |

### 5.4 Agent 文档必须回答的问题

1. 为什么需要这个 Agent？
2. 谁调用它，什么时候调用？
3. 调用前必须具备哪些数据和状态？
4. 它能读取哪些上下文？
5. 它明确不能读取什么？
6. 它可以调用哪些工具？
7. 工具调用顺序和预算限制是什么？
8. 输出必须遵守什么结构？
9. 它有没有修改数据库或业务状态的权限？
10. 哪些确定性规则不能被模型意见覆盖？
11. 什么条件表示完成，什么时候必须停止？
12. 失败后重试、修订、降级、隔离还是转人工？
13. 哪个 Agent 或模块接收它的输出？
14. 如何判断输出正确、稳定且适合上线？

## 6. 最小文档组合

项目早期先采用最小组合，避免产生大量只有标题的文档。

### 6.1 普通功能模块

```text
README.md
BUSINESS_FLOW.md
DATA_MODEL_AND_API.md
ACCEPTANCE.md
```

### 6.2 普通 Agent

```text
README.md
AGENT_SPEC.md
PROMPT_AND_TOOLS.md
EVALUATION.md
```

当业务出现复杂状态、多个外部依赖、自动重试、严格质量门槛或多个 Agent 协作时，再按照前述推荐目录拆分。

## 7. 业务流程图要求

1. 一张图只描述一个业务目标；题库生产、在线辅导和错误重验应分别绘制。
2. 每张图必须有明确入口、终点、条件分支和失败去向。
3. Agent、确定性工具、数据库和人工操作使用不同节点名称，不能笼统写成“系统处理”。
4. 状态变化必须显示原状态和目标状态。
5. 图后使用文字解释关键规则，不能只保留流程图。
6. 文档中的流程必须与当前代码一致；未来步骤需要明确标记为待办。

## 8. 数据、接口与状态文档要求

涉及数据对象时，至少说明：

- 稳定标识和业务主键；
- 数据所有者与访问范围；
- 必填字段及其业务含义；
- 内容状态和版本字段；
- 创建、修改、归档与删除规则；
- 与其他对象的关系；
- 审计与来源信息；
- 缓存和索引如何失效。

涉及接口时，至少说明：

- HTTP 方法和路径；
- 调用角色和授权规则；
- 请求、响应 DTO；
- `code + message + retryable` 错误响应；
- 幂等键和网络重试行为；
- 并发冲突和版本冲突；
- 降级状态与客户端展示方式。

## 9. 文档与代码同步规则

新增或修改功能时，应同时检查：

1. 需求或业务边界是否改变；
2. 业务流程是否增加新分支；
3. 数据对象、状态或迁移是否改变；
4. API、错误码或权限是否改变；
5. Agent 输入输出、提示或工具是否改变；
6. 日志、指标和评估方式是否改变；
7. 人工验收清单是否需要增加步骤；
8. 文档中心是否需要增加或修改链接。

文档描述代码事实时，应尽量链接到对应模块、迁移或接口文件。删除或移动文档时，先修复所有引用，避免留下失效链接。

## 10. 命名与放置规则

- 功能模块文档放在 `docs/module/<模块名称>/`；
- 单一 Agent 的专项文档放在 `docs/agent/<Agent 名称>/`；
- 跨多个 Agent 的编排文档放在项目级或对应业务模块，不复制到每个 Agent 目录；
- 当前项目沿用中文目录名与大写英文文件名；
- 一个主题只保留一个主文档，其他文档通过链接引用；
- 文档标题使用清晰的中文业务名称，文件名保持稳定，避免频繁改名。

## 11. 可复用的任务提示词

### 11.1 创建功能模块文档

> 为这个功能建立标准模块文档。至少包含模块说明、需求与边界、业务流程、数据对象、接口、异常处理和验收清单。存在状态变化时增加状态机文档，涉及外部服务时增加运行与故障策略文档。所有文档加入项目文档总目录，并区分已实现、待实现和未来设想。

### 11.2 创建 Agent 文档

> 为这个 Agent 建立标准 Agent 文档。说明职责与禁止事项、调用方、输入输出、上下文边界、工具权限、执行流程、停止条件、失败恢复、与其他 Agent 的交接关系及评估方案。文档内容必须对应当前真实代码，未实现部分明确标记为待办，并把文档加入 Agent 目录和项目文档总目录。

## 12. 文档完成标准

一组模块或 Agent 文档只有同时满足以下条件才算完成：

- 新成员能够仅通过文档解释业务目标和边界；
- 可以沿流程找到输入、输出、状态和失败去向；
- 可以找到对应数据库对象、接口与代码位置；
- 可以说明权限、幂等、并发和数据隔离规则；
- 可以执行本地流程或人工验收；
- 可以通过指标或评估判断质量；
- 所有目录链接可以直接点击；
- 未实现内容没有被描述为现有能力。
